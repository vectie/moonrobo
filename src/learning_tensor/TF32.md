# Optional startup CUDA FP32 precision control

This extension changes precision only after an explicit call. Loading the
plugin, opening a `Backend`, or using the existing tensor API does not select a
new precision policy. The training CLI now exposes an explicit optional
[`allow_tf32` policy](../learning_aligned_gpu/cmd/README.md#explicit-cuda-fp32-policy)
with stable identity and inference provenance; absent configuration stays on
the legacy path. The independent CUDA probe and a subsequent
[integrated N2 training gate](#actual-integrated-cli-training--2026-10-24) have
both passed on node 179. The earlier frozen training/microbatch plugin and the
separately verified telemetry-c plugin remain unchanged.

## Supported contract

The extension uses the **LibTorch 2.11** per-operation C++ API. CUDA matrix
multiplication, cuDNN convolution, and cuDNN RNN have separate settings. It never
mixes these with deprecated `allowTF32` flags or the global matmul-precision API.
PyTorch documents the separate controls and warns against mixing the old and new
interfaces: [CUDA precision documentation](https://docs.pytorch.org/docs/2.11/notes/cuda.html#tensorfloat-32-tf32-on-ampere-and-later-devices).
The enum overloads are version-specific: [2.11 Context.h](https://github.com/pytorch/pytorch/blob/v2.11.0/aten/src/ATen/Context.h)
and [Context.cpp](https://github.com/pytorch/pytorch/blob/v2.11.0/aten/src/ATen/Context.cpp).
Other LibTorch minor versions explicitly report unsupported. A CPU/non-CUDA
build, no accessible CUDA device, or unavailable cuDNN also prevents setting.

```moonbit
let backend = @tensor.Backend::open(plugin)
guard backend.has_cuda_fp32_control() else { fail("rebuild required") }
let before = backend.cuda_fp32_settings()
let actual = backend.configure_cuda_tf32(
  matmul=true,
  cudnn_conv=false,
  cudnn_rnn=false,
  before_first_tensor=true,
)
```

`before_first_tensor=true` is an explicit acknowledgement of a **process-global,
startup-only** mutation. Configure before creating any tensor through this
plugin and before external LibTorch work. One shared mutex protects all Backend
handles of the loaded plugin. The first valid tensor-creation attempt, including
a CPU tensor, permanently closes the setter's startup window; a fresh Backend
does not reopen it. NCCL integer-control creation also closes this window even
when it precedes ordinary tensor creation. Readback remains available. The creation hook changes no
math, RNG or synchronization policy. It cannot intercept external LibTorch
calls, independently loaded plugin copies, or concurrent environment changes;
the caller must prevent those. A failed mutation/readback requires exiting the
process rather than continuing training.

The returned `CudaFp32Settings` records the three resolved Context precision
values (`BackendDefault`, `IEEE`, or `TF32`), both relevant environment overrides,
cuDNN availability, the startup lock, and three permission classifications.
`LibraryMayUse` means that this Context/override combination permits TF32. It
does **not** prove a particular kernel uses TF32, establish hardware support,
change tensor storage dtype, or enable mixed-precision autocast. This probe does
not exercise cuDNN convolution/RNN kernels.

Environment values are captured when the plugin loads and must remain fixed.
Only unset, `0`, and `1` are accepted; unknown or subsequently changed values
fail explicitly.

| Runtime setting | Behavior |
| --- | --- |
| `NVIDIA_TF32_OVERRIDE=0` | TF32 requests fail before mutation; readback reports runtime blocking even if the Context itself says TF32. IEEE requests remain allowed. |
| `NVIDIA_TF32_OVERRIDE=1` | Readback marks permission unconfirmed; configuration refuses it because this extension does not establish its enable semantics. Unset it before launch. |
| `TORCH_ALLOW_TF32_CUBLAS_OVERRIDE=1` | An IEEE matmul request is rejected; a conflicting existing IEEE Context readback is marked unconfirmed. |
| Overrides unset or `TORCH_ALLOW_TF32_CUBLAS_OVERRIDE=0` | Permission follows the resolved operation-specific Context setting. |

The driver-level zero override takes precedence over PyTorch settings; see the
[official CUDA environment variables](https://docs.pytorch.org/docs/2.11/cuda_environment_variables.html).
The extension does not infer successful enablement from an environment variable.

## ABI compatibility and local checks

The loader remains ABI **2**. Two optional symbols are discovered with `dlsym`:
`mr_tensor_cuda_fp32_settings_v1` and
`mr_tensor_configure_cuda_tf32_v1`. Missing symbols leave ordinary tensor calls
usable; querying/configuring this extension raises an explicit error rather than
inventing a default. Readback is a checked, borrowed seven-Int32 output buffer.
Only a complete successful read is decoded and exposed to MoonBit.

Local validation used a newly built **LibTorch 2.9.1 CPU** plugin under a distinct
filename. Two integration tests passed for explicit CPU rejection, mandatory
startup acknowledgement, old-plugin missing-symbol rejection, and unaffected
ordinary CPU tensor arithmetic. Two decoder tests passed for operation-specific
precision, override classification and malformed native fields. The fixed-input
probe test passed; its executable and build wrapper compile. These checks do not
compile or execute the version-gated 2.11 CUDA-positive branch. The separate
Spark deployment below subsequently compiled and exercised that branch.

## Independent bounded GPU probe

Build only the new target and run each mode in a **fresh bounded process** with
the exact new plugin. Preserve the image/plugin/executable hashes, command,
environment, stdout, stderr, exit status and OOM flag for each run.

```sh
moon build src/learning_tensor/tf32_probe --target native --release
TF32_PROBE=/absolute/tf32_probe.exe
TF32_PLUGIN=/absolute/new/libmoonrobo_learning_tensor.so
env -u NVIDIA_TF32_OVERRIDE -u TORCH_ALLOW_TF32_CUBLAS_OVERRIDE "$TF32_PROBE" "$TF32_PLUGIN" ieee
env -u NVIDIA_TF32_OVERRIDE -u TORCH_ALLOW_TF32_CUBLAS_OVERRIDE "$TF32_PROBE" "$TF32_PLUGIN" tf32-matmul
env -u NVIDIA_TF32_OVERRIDE -u TORCH_ALLOW_TF32_CUBLAS_OVERRIDE "$TF32_PROBE" "$TF32_PLUGIN" tf32-all
env -u TORCH_ALLOW_TF32_CUBLAS_OVERRIDE NVIDIA_TF32_OVERRIDE=0 "$TF32_PROBE" "$TF32_PLUGIN" override-negative
```

The three positive modes read all three operation settings before and after an
explicit configuration. They verify shared state through a second Backend,
missing-acknowledgement refusal, and the shared startup lock after tensor
creation. Each computes a deterministic **256×256** Float32 CUDA matmul and a
Float64 CUDA reference from the same exactly representable inputs. No RNG is
used. Reports include max absolute error, RMS error and relative L2 error over
65,536 outputs. The predeclared relative L2 bound is **0.005**, a smoke bound
separate from all training/microbatch equivalence tolerances. It does not require
the TF32 result to differ from IEEE and does not claim kernel dispatch or speed.

The negative mode requires `NVIDIA_TF32_OVERRIDE=0`, proves the TF32 request was
refused with no settings mutation, then configures IEEE and verifies GPU
arithmetic and late-setting refusal. A generic crash/error is not a passing
negative test. Every probe failure reports `status: failed` and exits nonzero.

Tensor payload is about 2.25 MiB, with a few MiB of bounded host arrays;
CUDA context and vendor workspace allocations are additional. Use the existing
8 GiB/zero-swap/2-CPU container and a process watchdog rather than treating the
payload estimate as total memory. No training, physics, NCCL or full-model
allocation runs. No production memory cap, 65% admission rule, or physics
reserve changes.
